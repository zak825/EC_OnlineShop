# 購入確認画面_設計処理

## 画面遷移

```
購入画面 ──【購入】──→ 購入確認画面 ──【確定】──→ メイン画面
   ↑  ←──【キャンセル】──┘
```

---

## 要件

| 要件 |
|---|
| 購入する商品の情報・数量・合計金額と、配送先（ログインユーザーの名前・郵便番号・住所・電話番号）を表示する |
| 確定ボタン・キャンセルボタンを配置する |
| 確定ボタン押下で購入を確定し、対象商品の在庫を購入数量分減らしてメイン画面へ遷移する |
| キャンセルボタン押下で購入画面へ戻る |

## 検討すべき要件

| 検討すべき要件 | 優先度 | 結果 |
|---|---|---|
| ログインしていない／セッション切れの場合はメッセージを出してログイン画面へ遷移し、ログイン成功後は購入画面からやり直させる | 高 | ⇒採用 |
| SQLへの不正なアクセスへの対策（SQLインジェクション） | 高 | ⇒採用 |
| 確定直前に他のユーザーが購入して在庫が足りなくなった場合の対策（同時購入） | 高 | ⇒採用 |
| 在庫の減算と購入履歴の登録を同時に行う（どちらかだけ成功しないようにする） | 高 | ⇒採用 |
| 確定ボタンの二重押し対策 | 中 | ⇒採用 |
| 購入完了メッセージを表示する | 中 | |
| 出品者に購入されたことを通知する | 低 | |

## 詳細設計書

| ユーザーの操作 | ステップ | 処理内容 | YES | NO |
|---|---|---|---|---|
| 画面を開く | 1. ログイン済みか確認する | セッションにログイン済みフラグがあるか確認する | ステップ2へ | 「セッションの有効期限が切れました。再度ログインしてください。」を表示し、ログイン画面へ遷移する（ログイン成功後はメイン画面へ） |
| | 2. 購入情報の有無を確認する | セッションに商品IDと数量があるか確認する | ステップ3へ | メイン画面へ遷移する |
| | 3. 購入情報を表示する | セッションの商品IDで Sales を、ユーザーIDで UserData を取得し、数量・合計金額（値段×数量）と配送先を表示する | | |
| キャンセルボタンを押す | 1. 画面遷移を行う | 購入画面へ遷移する（商品IDを渡す） | | |
| 確定ボタンを押す | 1. セッションが有効か確認する | ログイン済みフラグと、商品ID・数量がセッションに残っているか確認する | ステップ2へ | 下記「セッション無効時」の処理へ |
| | 2. SQLインジェクションのチェックを行う | プレースホルダ（パラメータ化クエリ）を使用する | ステップ3へ | |
| | 3. トランザクションを開始する | 以降のDB更新をまとめて扱う | ステップ4へ | |
| | 4. 在庫を引き当てる | Sales.Stock から購入数量を引く（条件：在庫 ≧ 購入数量 かつ 自分の出品でない） | ステップ5へ（引き当て成功） | ロールバックし、エラーメッセージ「在庫が不足しているため購入できません。」→ 購入画面へ（引き当て失敗） |
| | 5. 購入履歴を登録する | Purchase に購入者・商品ID・数量・単価・購入日時・発送フラグ(0)を登録する | ステップ6へ | ロールバックし、エラーメッセージ「購入に失敗しました。」→ メイン画面へ |
| | 6. コミットする | トランザクションを確定する | ステップ7へ | |
| | 7. セッションの購入情報を削除する | セッションから商品IDと数量を削除する | | |
| | 8. 画面遷移を行う | 「購入が完了しました。」を表示しメイン画面へ遷移する | | |

### セッション無効時

| ステップ | 処理内容 |
|---|---|
| 1. 購入処理を中止する | DB更新は一切行わない（購入は確定させない） |
| 2. メッセージを表示する | 「セッションの有効期限が切れました。再度ログインしてください。」 |
| 3. 戻り先を設定する | フォームの hidden 項目で送られた商品IDを戻り先としてURLパラメータに付ける（数量は引き継がない） |
| 4. 画面遷移を行う | ログイン画面へ遷移する |
| 5. ログイン成功後 | 戻り先の購入画面へ遷移し、在庫・出品者チェックからやり直す。戻り先がなければメイン画面へ |

- セッション切れ中に在庫や値段が変わっている可能性があるため、確認画面ではなく購入画面からやり直させる
- hidden の商品IDは書き換えられる可能性があるが、購入画面で存在・在庫・出品者を再チェックするので問題ない

## 使用テーブル

| テーブル | 操作 | 使用カラム |
|---|---|---|
| Sales | SELECT / UPDATE | ProductID, ProductName, Price, Userid, Stock, UpdateUserId, UpdatedDateTime |
| UserData | SELECT | Userid, UserName, ZipCode, Address, TEL |
| Purchase | INSERT | PurchaseID, ProductID, BuyerUserid, Quantity, UnitPrice, SoldDate, ShippingFlag, InsertUserId, InsertDateTime |

## テーブル変更案（要相談）

在庫が2個以上あると購入者が複数になるため、テーブル定義例の Sales にある「購入者・発送フラグ・購入日時・評価値・レビュー」は1行では持てません。そこで次のように変えることを提案します。

**Sales に追加**

| 論理名 | 物理名 | データ型 | 桁数 | NULLABLE | 備考 |
|---|---|---|---|---|---|
| 在庫数 | Stock | int | 4 | NOT NULL | 出品時に登録、購入ごとに購入数量分減らす |

**購入履歴 Purchase（新規）**

| 論理名 | 物理名 | データ型 | 桁数 | NULLABLE | 主キー | 外部キー | 備考 |
|---|---|---|---|---|---|---|---|
| 購入ID | PurchaseID | int | 8 | NOT NULL | ○ | | 自動採番 |
| 商品ID | ProductID | int | 8 | NOT NULL | | ○ | Sales |
| 購入者ID | BuyerUserid | int | 8 | NOT NULL | | ○ | UserData |
| 数量 | Quantity | int | 4 | NOT NULL | | | 1以上 |
| 購入時単価 | UnitPrice | int | 8 | NOT NULL | | | 後で値段が変わっても購入時の金額を残す |
| 購入日時 | SoldDate | datetime | 8 | NOT NULL | | | |
| 発送フラグ | ShippingFlag | bit | 1 | NOT NULL | | | 0:未発送 1:発送済 |
| 評価値 | Score | int | 4 | NULL | | | 受け取り後に入力 |
| レビュー | Review | text | 100 | NULL | | | 受け取り後に入力 |
| （共通項目） | InsertUserId 〜 UpdatedDateTime | | | | | | Common と同じ |

- Sales からは BuyerName / ShippingFlag / SoldDate / sucre / revwe を Purchase に移す
- 発送通知・レビューは購入ごとに Purchase の行に対して行う
